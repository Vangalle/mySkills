# Defining Subproject Context

Preserve **what the project is** before **what this round does**. A technical skeleton is an implementation state, not a product identity.

## Entry gate

Apply only when BOTH are observable in the request/context:
1. A new or extracted project has its own goal and responsibility boundary.
2. The current task prepares its project entry or cross-process/session handoff materials.

Completing deficient materials from that same creation/extraction qualifies. A task named “subproject”, a new folder/worktree, another agent, or the word “handoff” alone does not. If the gate fails, continue the original task without this workflow, extra documents, or qualification questions. Continuing an already-described project is outside this gate.

## Gather before drafting

Read the relevant confirmed requirements, corrections, parent-project overview and existing child materials. Separate confirmed facts, proposals and unknowns; retain compact source references accessible to the recipient. Parent permissions do not authorize child access to private inputs or production resources.

If essential identity is unavailable, mark it unknown and ask one focused question about the missing users/problem/boundary. Known implementation can still be recorded; label the handoff incomplete rather than inventing a product from libraries or filenames.

## Required content, in order

These are content slots, not mandatory headings or new files. Preserve existing user structure.

| Slot | Required meaning |
| --- | --- |
| Identity | What kind of product/tool it is, who uses it, and the outcome it provides. |
| Origin | Parent context, unmet need/conflict, and why a separate project exists. |
| Whole flow | Actors → inputs → processing → outputs → recipient/use; diagram complex relationships. |
| Boundary | Child responsibilities, parent/neighbor responsibilities, non-goals, dependencies and fixed constraints. |
| Project success | Observable end-to-end conditions; identify unverified assumptions. |
| This round | Scope, actual implementation, verification evidence, missing pieces, next step and blockers. |

Keep three subjects distinct: **whole-project goal / round scope / observed state**. “Analysis not implemented this round” does not mean “analysis outside the product”. Passing protocol tests does not establish product success.

## Place without duplication

- Project entry: stable identity and whole-project context before implementation detail.
- Handoff: begin with a compact identity + origin + flow/boundary recap, reference the canonical entry, then record round state and next action. A bare “read README” is not the recap.
- Existing complete context: reuse it; patch only missing slots. No compulsory README/HANDOFF/AGENTS file set, repeated approval ceremony, or rewrite of accurate sections.

For example: “A seller-side local evidence application: private sessions cannot go to the market, but self-entered usage numbers are insufficient. Seller input → approved local processing → minimal report/evidence → market verification. Review/payment remain in the market. The Rust protocol skeleton is not yet that working application.” Cryptography is the means, not the product.

## Cold-reader check

Using only the recipient's materials, answer: Why does this exist? For whom? What complete flow does it own? What stays elsewhere? What proves project success? What works now and what is next?

Patch unanswered slots before claiming handoff readiness; keep unresolved facts explicit. Under a short word budget, compress technical inventory first, preserving identity and boundaries. Explain conclusions directly in chat; documents are agent context, not user homework. Preparing materials does not authorize launching an agent: follow the user's launch choice and platform handoff tooling separately.
